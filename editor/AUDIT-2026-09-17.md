# Starlight engine and native editor — audit and fixes

Date: 2026-09-17. Delivered editor: `editor/bin/audit-release/Starlight.Editor.exe`. Root launcher and both existing desktop shortcuts now point to this build; prior release binaries and shortcut backups remain available. No optimizer jobs, original SampleGame source, Starbus services, or user scenes were changed.

## Outcome and scope

The reported Projects & Presets crash was reproduced through its failing WPF shell API, fixed, and checked through the actual editor UI. The editor, native viewport/Jolt build, and project launcher compile successfully. All **13 editor check modes** pass after correcting obsolete test assumptions. Both Empty and SampleGame/club actually launch and exit successfully, using temporary native-resolution presets.

This is a bounded audit of the implemented paths, not a proof of absence of all memory defects. One graphics-environment handle-growth issue remains reproducible outside Starlight. Unsupported feature requests and untested cases are listed explicitly below.

### Root cause and atomic repair

`Path.Combine(Workspace, "Starlight-Engine/deep")` preserved the embedded forward slash. Appending `projects` yielded a mixed-separator path accepted by filesystem APIs but rejected by WPF's shell item parser. `ShowDialog(this)` was outside the existing try/catch, so its exception terminated the process before project JSON was even read. It was not a DXR, scene graph, or preset parser crash.

- Canonicalize existing folder paths with `Path.GetFullPath`, reject missing/invalid folders before shell use: [editor/DialogHistory.cs:10](D:/projects/Starlight-Engine/editor/DialogHistory.cs:10).
- Shared dialog wrapper catches picker exceptions and records their stack: [editor/DialogHistory.cs:23](D:/projects/Starlight-Engine/editor/DialogHistory.cs:23).
- Project path is canonicalized; schema/default scene are validated before committing selection; switching projects clears the old preset: [editor/ProjectWindow.cs:27](D:/projects/Starlight-Engine/editor/ProjectWindow.cs:27).
- Scene, model, music, project and preset pickers use the same history/error handling. Save only commits a new scene filename after a successful save: [editor/MainWindow.xaml.cs:68](D:/projects/Starlight-Engine/editor/MainWindow.xaml.cs:68).

UI verification: Main menu → Projects & presets → Open project opened normally; selecting `Empty.star` returned a live panel with “Project selected. Load a preset next.” Opening the picker again started in `deep\projects\Empty`. Cross-session disk reload is also covered by the managed audit. History is stored in `%LOCALAPPDATA%\Starlight\dialog-folders.json`, with per-purpose entries and a shared fallback. Writes are atomic; corrupt history is ignored safely.

**Exact persistence limit:** successful selections persist. A stable Windows dialog ClientGuid preserves accepted shell locations. Browsing to a different directory and cancelling returned to the last accepted directory on the next open in this Windows build. Cancel-only navigation is therefore not claimed as persisted.

## 2. Legacy dump routing

### Root cause

The process inherited this user-level environment variable, also observed in the current process:

```text
DOTNET_DbgEnableMiniDump=1
DOTNET_DbgMiniDumpType=2
DOTNET_DbgMiniDumpName=C:\Users\Chaos\AppData\Local\SampleServer\dumps\worldserver.%p.dmp
```

The original editor had no application-specific crash handler or override. The inspected WER LocalDumps entries were NVIDIA-specific, not an editor routing rule. There is no Starlight dump-redirection call stack to invent: this was inherited configuration. The managed exception stack above identifies the crash that exposed it.

### Repair and verification

- [editor/Diagnostics.cs:14](D:/projects/Starlight-Engine/editor/Diagnostics.cs:14) sets editor process overrides and registers an unhandled-exception stack report. The launcher sets overrides before starting .NET. Global/user environment settings remain unchanged for other applications.
- [editor/Diagnostics.cs:23](D:/projects/Starlight-Engine/editor/Diagnostics.cs:23) writes a real `MiniDumpNormal` through `MiniDumpWriteDump` into `%LOCALAPPDATA%\Starlight\Diagnostics\Editor`. The `.json` sibling records the managed exception stack. The fatal handler does not mark unknown exceptions handled and continue in damaged state.
- Native launcher: [deep/engine/crash_diagnostics.h:11](D:/projects/Starlight-Engine/deep/engine/crash_diagnostics.h:11) records SEH exception pointers in `%LOCALAPPDATA%\Starlight\Diagnostics\Engine`. A deliberately crashing **isolated test executable** exercised the handler and produced a valid MDMP file: [native-crash-routing.json](D:/projects/Starlight-Engine/editor/checks/audit-20260917/native-crash-routing.json).
- Native launch errors now default to an engine diagnostic file per PID. Editor preset checks pass an explicit per-request `--error` path, eliminating stale/shared launch-error reads: [editor/ProjectWindow.cs:41](D:/projects/Starlight-Engine/editor/ProjectWindow.cs:41), [deep/src/runtime.cpp:42](D:/projects/Starlight-Engine/deep/src/runtime.cpp:42).

Dump creation is best-effort, in-process. This is not an out-of-process crash service or a guarantee under stack exhaustion, severe heap corruption, or disk failure. The managed dump writer was exercised directly; the normal user editor was not intentionally crashed.

These measurements demonstrate the tested variance/reprojection behavior; they do **not** prove universal zero ghosting, preserved texture detail in every case, or zero NaNs for untested inputs. No new 4K performance claim is made from these functional runs.

## 5. Open issues, unsupported paths and limits

1. **Residual swap-chain handle growth:** original create/destroy loop grew `[265,269,...,301]`; after closing Starlight-owned handles it grew `[263,265,...,281]`. The remaining objects are a Mutant and Section named `{2627E361-24E2-4F14-99ED-A20D0685D8DD}_v22...`. A separate program using only Windows/D3D12/DXGI swap-chain creation reproduces `[242,244,...,256]`; plain device/pipeline creation remained flat. See `device-lifecycle.cpp`, `device-lifecycle.log`, `handle-types.json`, `handles-before.json` and `handles-after.json`. This isolates the remaining behavior to the system graphics path in this environment, but does not establish which driver, overlay, or Windows component owns it. Do not close unknown handles by enumeration. Resize currently rebuilds the viewport; reusing the device/swap chain and further graphics-stack investigation are follow-up work.
2. **Cancel-only folder navigation:** the dialog remembers successful choices, not a directory merely browsed before cancellation, as noted above.
3. **Project creation and formats:** the existing panel selects manifests, reconciles/saves presets and launches modules. It has no project-creation wizard. `.star` and `.startest` are JSON; there is no TOML/native binary preset parser to test.
4. **Scene scope:** replacement/unload/reload paths were tested. There is no implemented additive-scene composition lifecycle or separate scene graph resource manager. Managed imported-model caching is still session-scoped; a long session importing many unique assets can retain those models until the editor exits. No multi-hour stress or address-sanitizer run was performed.
5. **Asset scope:** GLB static geometry import and malformed data checks ran, including the existing fox model. Skeletal playback, animation import, texture material ingestion and general VR-asset conformance are not implemented by this static preview loader. Sparse/external-buffer GLBs remain explicitly unsupported. The import limits are desktop safety bounds, not unbounded streaming.
6. **UI scope:** existing dock, popup, full-screen, interaction, terrain and camera tests ran. This editor does not have persistent arbitrary docking layouts or multi-monitor split viewports; those cannot truthfully be marked passed. Multi-monitor physical dragging and every DPI/narrow panel combination were not exhaustively tested. The RR short label remains in the delivered UI.
7. **Telemetry scope:** actual FPS/GPU/ray/denoiser/AS tier metrics and JSON reports were generated and parsed. The current logs do not provide comprehensive VRAM allocation/live-object inventories or full draw-call accounting. File writers use scoped handles for reports; the active native logger intentionally stays open for process lifetime. No forced disk-full or network-filesystem failure campaign was run.
8. **Native ABI contract:** handles other than the specifically hardened frame entry point still require valid live viewport ownership. Arbitrary stale handles, device-removal injection and every out-of-memory path were not exercised. An unbounded `WaitForSingleObject` remains in the shared fence-wait path and merits a device-loss recovery pass; no hang occurred in these tests.

The result is **critical fixes delivered with passing available regression suites and documented remaining risks**, not an unconditional clean bill of health.
