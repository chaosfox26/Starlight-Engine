# Starlight current-engine deep analysis

The main purpose is to give a future assistant a reusable understanding of **what Starlight is, its features, workflows, system relationships and completion boundaries**, without repeatedly investigating source code. The tool combines versioned explanations, source evidence, actual catalogue metadata and dated validation. Byte inventories and code indexes are supporting evidence, not the main reading experience. Historical documents are explicitly outdated.

Read `STARLIGHT-START-HERE.md` first, then `STARLIGHT-FEATURE-REFERENCE.md` or `STARLIGHT-WORKFLOWS.md` as needed. `engine-knowledge.json` stores the same structured context for tools. `KNOWLEDGE-COVERAGE.md` explains freshness and unmapped areas. The existing technical summary, source atlas and byte census remain available for targeted investigation.

Source-supported implementation, partial product scope, roadmap metadata and passed/failed runtime checks are separate. No catalogue label or keyword match automatically means a feature is complete. New feature meanings require updating the curated rules in `knowledge_report.py`; the tool does not claim automatic semantic understanding of arbitrary code.

## Run

Feature reports and Run both now also generate `ENGINE-COMPARISON.md` and `engine-comparison.json`. The desktop launcher has an Open engine comparison button. The initial mapping covers animation, gameplay authoring, standalone builds and starting/learning against official Unreal Engine 5, Unity 6 and Godot 4 documentation. Remaining Starlight areas are explicitly listed as unmapped. Competitor claims are curated, dated and flagged for review after 90 days; each audit does not automatically research the web. Source support, linked runtime evidence and documented competitor behavior remain different evidence classes. No performance ranking is generated without matched cross-engine measurements.

To compare a completed audit without rerunning tests, use `engine_comparison.py --from-run <saved audit> --output <new folder>`. This preserves the saved Starlight assessment and copies any review notes alongside the comparison. It does not assert that the snapshot matches later code. Run `test_engine_comparison.py` for unknown-coverage, reference-age and unmeasured-performance safeguards.

The consolidated entry point is `audit_engine.py --root <repository> --output <fresh external folder> --audit-mode features|errors|both`. Features performs source inventory and saved-evidence analysis. Errors builds an isolated `out/audit-engine` tree, discovers registered checks and runs native lifecycle/render/visible checks plus explicit denoiser/fallback fixtures. Both runs those stages and generates the source briefing with linked evidence. Error/combined mode returns 4 when a report was produced but stages failed or did not run. This must not be presented as a clean pass.

The reusable native desktop candidate has **Feature report**, **Error checks**, and **Run both** buttons; all three are disabled during a run and restored afterward. Each pass snapshots reporting scripts and gets a fresh output folder. The desktop shortcut should point to the validated candidate only after the live workflow check. Original evidence is retained.

The coordinator shares process execution with `run_editor_parity_checks.py`, including bounded waits, logs, and cleanup of owned child processes. Session coverage is delegated to the native harness's traced lifecycle run instead of executing the same session suite twice. Separate idle controls, visual stages, image-quality checks and fallback checks retain separate identities.

From the Starlight repository, using the existing Python and Visual Studio C++ installation:

```powershell
python tools/audit/test_deep_analysis.py
python tools/build/build_deep_analysis.py --build-dir out/analysis-tool --launch
```

Use a fresh build directory if the GUI executable is open. The native progress GUI stays open at completion; closing it while active minimizes it so the analyzer can finish. Open summary/evidence buttons provide the results. The launcher immediately returns and does not poll. Tell the assistant “Completed” when ready for review.

The analyzer uses four I/O workers by default, reads regular files under the repository including ignored/build/Git/vendor/historical files, except the root analysis, publication and _quarantine directories, and records SHA-256 plus named NTFS stream hashes. Output may be outside the repository or in a fresh run folder under analysis/. The excluded folders prevent recursive self-inventory and duplicate publication-source counts; run-state.json records those exclusions. A second directory enumeration detects path/size/time changes. Every inaccessible file or skipped reparse point is reported. The source rules inspect current candidate modules separately from archived source and generated byte arrays.

## Limits

### Guarded source lookup

`source_lookup.py` queries the existing `source-index.json`; it does not create another index or edit files. Combine `--file` (relative glob), `--symbol` (exact declaration), `--kind`, `--text` (literal substring), `--line`, and `--expect` (exact full line). All supplied filters must match the same line. `--context` supplies up to 50 surrounding lines.

Example: `python tools/audit/source_lookup.py --root D:/projects/Starlight-Engine --run D:/projects/Starlight-Engine/analysis/run-20260923-032802 --file editor/cpp/*.cpp --symbol Update --text camera`

Exit status: 0 unique, 1 absent, 2 ambiguous, 3 blocked. It verifies the saved index seal and current hashes for every file in the selected file scope; stale, missing, inconsistent or unreadable files block a clean result. A fresh scan is required after changes. Matches include source hashes and numbered context. Recheck the hash immediately before editing: the lookup is not an atomic edit transaction. The index covers selected source candidates and lexical declarations, not every reference, overload relationship, new unindexed file, or compiler-resolved call graph. A unique match identifies a location; it does not certify a proposed change or eliminate the need to inspect callers, contracts and relevant tests.

Run guard checks with `python tools/audit/test_source_lookup.py`.

This is not an atomic filesystem snapshot, exhaustive static compiler analysis, decompiler, sanitizer, profiler or runtime proof. Source detection is lexical and report interpretations are versioned in the tool; missing markers are visible. External SDKs/assets, directory metadata, ACLs and deleted/unallocated content are not hashed. Named streams on regular files are covered; directory streams are not. Duplicates are logical per-path bytes, not physical disk usage. Existing binary artifacts are not assumed to match current source. Reports cannot certify zero bugs, leaks or races, or validate maximum FPS.

Main deliverable: `STARLIGHT-START-HERE.md`. Feature/workflow detail follows its links. Technical appendix: `Starlight-Current-Engine-Summary.md`; exact inventory: `byte-manifest.jsonl`; scan limitations: `run-state.json`.

To improve the documents using a completed run without another full audit:

```powershell
python tools/audit/knowledge_report.py --from-run D:/projects/Starlight-Engine/analysis/run-20260918-015935 --output D:/projects/Starlight-Engine/analysis/knowledge-new --root D:/projects/Starlight-Engine
```

This verifies required saved-artifact hashes and rehashes indexed product source/build inputs, then writes a separate knowledge pack. It refuses changed/missing product inputs or an existing output folder. It does not discover new/unindexed product files or perform new runtime tests; that limitation is recorded in the generated provenance. Use a fresh full scan after implementation changes. Original evidence remains unchanged.

## Connected reporting — 23 September

Runtime evidence supplied through `--extra-evidence` is explicitly identified in the overview before historical cohorts. This means supplied input, not necessarily freshly executed tests: reuse and source/build matching remain separately reported. Windows paths are normalized for recognition while original evidence paths are retained. Failed visible starts with zero completed checks remain failures; intermediate progress/status records are not final results.

For document-only regeneration, `knowledge_report.py --extra-evidence <runtime-evidence.json>` accepts an explicit saved runtime bundle alongside the sealed source run. Its path and hash are recorded in report provenance; it does not relabel old test builds as current. Always use a new output folder and preserve the original report.

Visible editor evidence is validated by required named checks rather than an obsolete fixed total. Required checks must occur once, pass, remain foreground, and capture successfully. Additional checks must also pass. The asset walkthrough uses a temporary native-object fixture and does not open or change the user's remembered asset folder; interactive OS file-dialog verification remains separate.

The analyzer discovers JSON evidence recursively under audit-runs, including previously unknown folder families. Invalid or oversized records (over 2 MiB) are explicitly flagged rather than interpreted. CSV, images and other artifacts remain byte-inventoried, not automatically interpreted.

`feature_evidence.py` generates `feature-status.json` and `GENERATED-FEATURE-BRIEFING.md`. It joins records with schema `starlight.feature-evidence.v1` to stable feature IDs derived from subsystem names. Records declare `features`, `outcome`, `workload`, `build` (path and SHA-256), `sourceHashes` (relative source paths to SHA-256), and `issues` (ID/status/summary). Unknown feature IDs and legacy records require review. Conflicting/open issues remain visible; a later pass never automatically closes them.

The editor parity runner now writes a `.feature-evidence.json` sidecar with pre/post execution input checks and process exit status. It records the observed executable, not proof that this executable was built from the observed source. Source matching does not establish transitive build-input coverage. Existing historical results are never retroactively given current hashes. Other test producers can call `capture_record` during their own execution and adopt this same schema; they have not all been migrated.

Curated implementation descriptions and product requirements still require maintenance when semantics change. Automatic discovery and connected evidence reduce duplicated reporting work; they do not perform arbitrary semantic inference or replace visual acceptance. Changed product files, unmapped files and unsupported evidence remain explicit coverage warnings.
